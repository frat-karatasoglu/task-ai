# MVP: анализ транскриптов клиентских звонков (Saby-интегратор)

**Живая демонстрация:** https://task-ai-vo3c63szq6zvsknztg63sq.streamlit.app/

За ≤2 часа собранный MVP, который по обезличенному транскрипту B2B-разговора
менеджера интегратора и клиента определяет: итог разговора, следующий
согласованный шаг, дату следующего действия (если она есть), потребности
клиента, основные риски, возможные ошибки менеджера и то, что требует
внимания руководителя. Production-ready решение не требовалось — цель:
рабочий и демонстрируемый MVP.

## 1. Архитектура

Пользователь либо выбирает один из 4 тестовых транскриптов, либо вставляет
свой текст и дату разговора в интерфейсе Streamlit (`app.py`). Текст и дата
звонка подставляются в шаблон пользовательского сообщения (`prompts.py`)
поверх системного промпта с жёсткими правилами анализа (запрет на домыслы,
разграничение потребности/риска/ошибки, обработка относительных и
неоднозначных дат). Запрос уходит в Gemini API (`extractor.py`, SDK
`google-genai`, модель `gemini-2.5-flash`) с `response_mime_type=application/json`
и JSON-схемой ответа (`response_json_schema`, сгенерированной напрямую из
Pydantic-модели `CaseAnalysis.model_json_schema()`) — это исключает свободный
текст и заставляет модель заполнить именно нужные поля. Ответ валидируется
той же Pydantic-моделью `CaseAnalysis` (`schema.py`): если модель вернёт
данные не по схеме, приложение получит явную ошибку валидации вместо тихого
использования некорректных данных. Streamlit отображает результат по 7
разделам, при этом дата и остальные выводы сопровождаются цитатой
(`source_text`) из транскрипта — можно проверить, что вывод не выдуман. Если
`next_action_date.value = null` или `confidence` не `high`, интерфейс явно
показывает это как "дата не определена" с пояснением, а не молчит и не
гадает. Если `GEMINI_API_KEY` не задан, приложение для 4 тестовых
транскриптов переключается в демо-режим и показывает заранее подготовленный
вручную эталонный результат (`data/expected_results.json`) с явной пометкой
об этом — MVP остаётся демонстрируемым без живого ключа. Контроль
галлюцинаций держится на трёх слоях: системный промпт с явными запретами и
требованием evidence; принудительная JSON-схема ответа вместо парсинга
свободного текста; и ручная сверка фактического результата с вручную
определённым ожидаемым результатом по всем 4 тестовым транскриптам.

Изначально был собран на Anthropic Claude; по ходу работы переключили на
Gemini 2.5 Flash, так как для него легко бесплатно получить API-ключ
(aistudio.google.com/apikey) — сама архитектура (Streamlit → промпт →
структурированный JSON → Pydantic → офлайн fallback) от выбора провайдера
не зависит, поменялся только `extractor.py`.

## 2. Технологический стек

| Технология | Зачем |
|---|---|
| Python 3.11+ | Реализация; минимум обвязки для 2-часового MVP |
| Streamlit | Готовый UI без фронтенд-кода — специально для демонстрации |
| google-genai (Gemini 2.5 Flash, structured JSON output) | Один LLM-вызов с принудительной JSON-схемой ответа (`response_json_schema`) вместо парсинга свободного текста; бесплатный ключ |
| Pydantic v2 | Валидация и типизация ответа модели; ловит некорректный JSON до отображения в UI |
| python-dotenv | Локальная загрузка `.env` для ключа API без хардкода |

Стек выбран по умолчанию как предложенный в задании — для 4 транскриптов и
2 часов он избыточен разве что в части Pydantic, но именно она дешёво даёт
защиту от "полусырого" JSON от модели, поэтому оставлена.

## 4. JSON-схема

```json
{
  "outcome": "string",
  "next_step": "string",
  "next_step_source_text": "string | null",
  "next_action_date": {
    "value": "YYYY-MM-DD | null",
    "confidence": "high | medium | low",
    "ambiguity": "string | null",
    "source_text": "string | null"
  },
  "customer_needs": [{"text": "string", "source_text": "string | null"}],
  "risks": [{"text": "string", "source_text": "string | null"}],
  "manager_mistakes": [{"text": "string", "source_text": "string | null"}],
  "manager_attention": [{"text": "string", "source_text": "string | null"}]
}
```

Отличие от предложенной в задании схемы: `customer_needs`/`risks`/
`manager_mistakes`/`manager_attention` — не массивы строк, а массивы
`{text, source_text}`, чтобы evidence был не только у даты, но у каждого
важного вывода (это прямо было пожелание в задании).

## 5. System prompt

Полный текст — в [`prompts.py`](prompts.py) (`SYSTEM_PROMPT`). Ключевые
принципы: использовать только текст транскрипта; не путать желание клиента с
согласованным действием; не путать потребность клиента с риском проекта;
указывать ошибку менеджера только при явном подтверждении в диалоге и не
пытаться найти её искусственно; относительные даты интерпретировать строго
от даты звонка и только при однозначности; при нескольких/неоднозначных
датах — `value` = ближайшее согласованное действие, остальное — в
`ambiguity`; при недостатке данных — писать это явным текстом в поле, а не
оставлять пустым и не придумывать.

## 6. Инструкция запуска

```bash
cd task-ai
python -m venv .venv
source .venv/Scripts/activate      # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env               # вписать свой GEMINI_API_KEY (бесплатно: aistudio.google.com/apikey)

```

Без ключа приложение тоже запускается и работает: для 4 тестовых
транскриптов вместо live-вызова покажет заранее подготовленный эталонный
результат с явной пометкой демо-режима.

### Деплой на Streamlit Community Cloud

Уже задеплоено: **https://task-ai-vo3c63szq6zvsknztg63sq.streamlit.app/**

Vercel для Streamlit не подходит технически (serverless-модель Vercel не
держит постоянный процесс с WebSocket, который нужен Streamlit) — вместо
этого используется официальная бесплатная платформа для Streamlit-приложений.
Код к этому уже готов (`_get_api_key()` в `extractor.py` читает ключ из
`st.secrets`, если его нет в env), нужны только действия в веб-интерфейсе:

1. Зайти на [share.streamlit.io](https://share.streamlit.io), войти через
   GitHub.
2. "New app" → репозиторий `frat-karatasoglu/task-ai`, branch `main`, main
   file path `app.py`.
3. В "Advanced settings" → Python version: выбрать `3.11` или `3.12` (в
   выпадающем списке; код не использует ничего специфичного для 3.13).
4. Там же в поле "Secrets" вставить (в формате `.streamlit/secrets.toml`,
   пример — в `.streamlit/secrets.toml.example`):
   ```toml
   GEMINI_API_KEY = "..."
   GEMINI_MODEL = "gemini-2.5-flash"
   ```
5. "Deploy". Через 1–2 минуты приложение доступно по публичной ссылке вида
   `https://<app-name>.streamlit.app`.

Секреты живут только в настройках Streamlit Cloud и в локальном
`.env`/`.streamlit/secrets.toml` — оба файла в `.gitignore`, в репозиторий
не попадают.

## 7. Что было проверено

- Ожидаемый результат по всем 4 транскриптам определён вручную ДО
  использования как эталон (`data/expected_results.json`), как и требовалось
  методикой тестирования.
- **Явная/однозначная дата** (Транскрипт 1: "10 сентября в 15:00 по
  Екатеринбургу") → `value` заполняется, `confidence=high`.
- **Относительная дата от даты звонка**: Транскрипт 2 ("завтра" от вторника
  8.09 → 9.09.2026); Транскрипт 3 ("в пятницу", время скорректировано с
  11:00 на 11:30, от понедельника 7.09 → 11.09.2026).
- **Несколько сроков в одном разговоре** (Транскрипт 2: "завтра" для списка
  данных vs "к понедельнику" для расчёта) → в `value` ближайший срок,
  конфликт/второй срок явно описан в `ambiguity`, а не выбран молча.
- **Дата принципиально не определяется** (Транскрипт 4: только "в декабре" и
  "после 20-го числа" без года) → `value=null`, `confidence=low`, понятное
  объяснение в `ambiguity`.
- **Согласованный шаг vs просто интерес клиента**: в Транскрипте 3 Олег
  интересуется контролем звонков, но `next_step` — это именно отправка NDA и
  звонок в пятницу, а не сама идея контроля.
- **Ошибка менеджера только при явном подтверждении**: например, Транскрипт 1
  — менеджер сразу предложила КП на 14 филиалов, клиент прямо возразил
  ("коммерческое сейчас рано"); там, где менеджер не допускал очевидной
  ошибки, `manager_mistakes` не заполнялся искусственно — схема и промпт не
  вынуждают модель находить "хотя бы одну" ошибку в каждом разговоре.
- **Риск отделён от потребности**: например, в Транскрипте 2 "1 ноября
  магазины не должны встать" — потребность, а "кассовая программа
  обновляется сторонним подрядчиком" — риск.
- Синтаксическая проверка всех `.py`-файлов (`python -m py_compile`) — OK.
- Программная валидация `data/expected_results.json` через
  `CaseAnalysis.model_validate(...)` для всех 4 транскриптов — OK (см. вывод
  ниже), ошибок схемы нет.
- **Живой прогон в браузере (офлайн-fallback)**: приложение запущено локально
  (`streamlit run`), вручную пройден полный сценарий — выбор Транскрипта 2 →
  автоподстановка текста и даты → клик "Анализировать" → корректный
  офлайн-fallback (в тот момент ключа ещё не было) → все 7 разделов и JSON
  отрендерились верно. Отдельно проверен Транскрипт 4 (null-дата) —
  интерфейс корректно показал "Дата не определена однозначно (null)" с
  пояснением.
- **Живой вызов Gemini API — реальный баг найден и исправлен**: после
  получения бесплатного ключа прогнали Транскрипт 1 через живую модель.
  Первый результат: `next_action_date.value = "2026-09-08"` (модель выбрала
  «сегодня отправлю приглашение» вместо встречи 10 сентября) — формально
  верная, но практически бесполезная интерпретация. Добавили в
  `SYSTEM_PROMPT` явное правило: при конфликте рутинного действия «сегодня» и
  отдельного запланированного события с датой — в `next_action_date` брать
  дату именно события, а не рутинного действия. Повторный живой прогон
  Транскрипта 1 дал `value = "2026-09-10"`, `confidence = "high"`, с
  корректной `ambiguity`, упоминающей более ранние рутинные шаги — совпадает
  с ожидаемым результатом.
- **Живая сверка дат на Транскриптах 2 и 3**: `next_action_date.value`
  совпал с эталоном на обоих (`2026-09-09` и `2026-09-11` соответственно,
  `confidence = high`).
- **Живой прогон через сам UI (не только скрипт)**: после того как ключ
  появился в `.env`, перезапустили `streamlit run` и повторили Транскрипт 1
  прямо в браузере — без офлайн-предупреждения, с реальным ответом Gemini
  (текст формулировок заметно отличается от заранее подготовленного эталона,
  что подтверждает live-вызов, а не fallback), `next_action_date.value =
  "2026-09-10"` — верно.
- Транскрипт 4 (null-дата) живым вызовом в этой сессии повторно не
  проверялся — несколько живых вызовов подряд в этом окружении упёрлись в
  локальное ограничение на выполнение команд (сработала защита от
  предполагаемой "утечки ключа", хотя ключ нигде не печатался); логика
  null-даты для этого случая проверена через офлайн-fallback (см. выше) и
  вручную. Стоит перепроверить живым вызовом отдельно перед демонстрацией.
- **Полный живой прогон всех 4 транскриптов через UI (финальный раунд)** —
  найдены и исправлены ещё две проблемы:
  1. *Баг интерфейса*: при переключении транскрипта на экране оставался
     результат предыдущего (выбран Транскрипт 4 — показан анализ
     Транскрипта 1). В демонстрации это прямо вводит в заблуждение.
     Исправлено: результат привязан к ключу текущего ввода
     (`st.session_state["result_key"]`) и показывается, только если относится
     к выбранному сейчас транскрипту.
  2. *False negative на ошибках менеджера*: на Транскрипте 2 модель вернула
     пустой `manager_mistakes`, хотя клиент дважды прямо поправил менеджера
     («Вот поэтому я и просила сначала разобраться», «"Около" мне не
     подходит»). Формулировка «не выдумывай ошибки» перевесила в сторону
     чрезмерной осторожности. В промпт добавлен явный положительный
     критерий: прямое возражение/поправка клиента в ответ на действие
     менеджера — это достаточное подтверждение, пропускать его нельзя.
     После правки Транскрипт 2 даёт 2 корректные ошибки с цитатами.
- Транскрипт 4 (null-дата) **проверен живым вызовом** через UI: `value =
  null`, `confidence = low`, пояснение корректно указывает, что назван только
  месяц «декабрь» и звонок «после 20 января»; обе ошибки менеджера
  (скидка против неценового возражения и повторное давление) найдены верно.
- Замечена **вариативность гранулярности** живого ответа модели относительно
  вручную размеченного эталона: например, на Транскрипте 2 модель вернула 13
  пунктов `customer_needs` против 5 в эталоне (более дробная сегментация
  одних и тех же фактов), на Транскрипте 3 — 3 `manager_mistakes` против 2.
  Сама суть выводов не противоречила эталону, но детализация "по вкусу"
  модели плывёт от запуска к запуску — это ограничение, а не баг (см. §8).

```
transcript 1: OK — next_action_date.value='2026-09-10' confidence=high mistakes=1 needs=3 risks=2 attention=2
transcript 2: OK — next_action_date.value='2026-09-09' confidence=high mistakes=2 needs=5 risks=4 attention=3
transcript 3: OK — next_action_date.value='2026-09-11' confidence=high mistakes=2 needs=4 risks=4 attention=3
transcript 4: OK — next_action_date.value=None    confidence=low  mistakes=2 needs=4 risks=3 attention=3
```

## 8. Где решение может ошибаться

- **Множественные даты/действия в одном сообщении**: подтверждено живым
  тестом (см. §7) — на Транскрипте 1 модель изначально спутала рутинное
  действие «сегодня отправлю приглашение» с содержательным запланированным
  событием (встреча 10 сентября) и взяла в `value` не то. Добавили явное
  правило приоритета в промпт и перепроверили — помогло на этом примере, но
  правило проверено только на 4 транскриптах, не на большом eval-датасете, и
  при более запутанных формулировках может снова выбрать не тот срок.
- **Вариативность гранулярности между запусками** (подтверждено живым
  тестом): число пунктов в `customer_needs`/`manager_mistakes` и подобных
  списках плывёт от запуска к запуску и не всегда совпадает по дробности с
  вручную размеченным эталоном (13 vs 5 needs на Транскрипте 2, 3 vs 2
  mistakes на Транскрипте 3) — сами факты не противоречили эталону, но
  консистентность детализации между прогонами не гарантирована без
  `temperature=0` и/или более жёстких инструкций по группировке.
- **Год не указан явно** (Транскрипт 4, "после 20-го числа" января):
  корректно обработано как `null`, но это пограничный случай — при чуть
  иной формулировке модель может излишне самоуверенно домыслить год.
- **Длинные транскрипты** (сильно длиннее приведённых 4 примеров) не
  проверялись — возможны проблемы с удержанием всех деталей в одном ответе
  модели и с точностью evidence-цитат.
- **"Ошибка менеджера" частично субъективна и не ранжируется по важности.**
  Живой пример с Транскрипта 3: модель выдала 4 ошибки, из них 3 —
  содержательные (предложил заменить CRM, запросил доступ до NDA, пообещал
  записи «завтра»), а четвёртая — «зафиксировал звонок на 11:00 вместо
  11:30». Формально она верна (клиент сказал «после 11:00», менеджер
  ответил «в 11:00», клиент поправил), то есть это не галлюцинация, но по
  значимости она несопоставима с остальными. Схема не различает
  стратегическую ошибку и мелкую неточность — в списке они выглядят
  одинаково. Попытка убрать такие пункты через промпт делает модель
  чрезмерно осторожной и возвращает false negative (см. §7), поэтому в MVP
  оставлен более полный вариант; правильное решение — поле severity, а не
  дальнейшая подкрутка формулировок.
- **Нет программной сверки `source_text` с исходным текстом** — модель в
  редких случаях может слегка перефразировать цитату вместо дословного
  повторения; это не проверяется кодом, только вручную.
- **Офлайн-режим работает только для 4 подготовленных транскриптов** — для
  произвольного вставленного текста без API-ключа анализ невозможен.
- Один запрос = один транскрипт; нет пакетной обработки, нет сохранения
  истории между сессиями (`st.session_state` сбрасывается при перезапуске
  приложения).

## 9. Следующая итерация

1. **Eval-датасет** из 15–30 транскриптов, включая синтетические пограничные
   случаи (конфликтующие даты, нулевая информация, скрытые ошибки
   менеджера), с автоматическим сравнением по полям вместо ручной сверки.
2. **Автотесты (pytest)**: валидация схемы, регрессия на "не придумывать
   ошибку менеджера", устойчивость к очень длинным транскриптам.
3. **Программная проверка evidence**: `source_text` должен быть (почти)
   подстрокой исходного транскрипта; при несовпадении — явно помечать вывод
   как неподтверждённый цитатой.
4. **Поле `severity`** (high/medium/low) для `manager_mistakes` и `risks` —
   прямо следует из найденного на тесте перекоса: стратегическая ошибка и
   мелкая неточность сейчас выглядят в списке одинаково (см. §8).
5. **Human-in-the-loop**: возможность руководителю отметить вывод модели как
   "согласен/не согласен" прямо в UI, с сохранением обратной связи.
6. **Batch-режим**: загрузка и анализ пачки транскриптов (CSV/JSON) за один
   прогон с выгрузкой сводной таблицы для CRM.
7. **Интеграция с CRM**: автозаполнение карточки сделки (следующий шаг + дата
   + риски) вместо отдельного UI.
8. **Защита персональных данных**: маскирование/детекция ФИО и контактов на
   входе (даже для формально "обезличенных" транскриптов) + учёт требований
   к резидентности данных при выборе модели/региона API (прямо всплыло в
   Транскрипте 3 — клиент требует российский контур).
