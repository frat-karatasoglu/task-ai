# MVP: анализ транскриптов клиентских звонков (Saby-интегратор)

За ≤2 часа собранный MVP, который по обезличенному транскрипту B2B-разговора
менеджера интегратора и клиента определяет: итог разговора, следующий
согласованный шаг, дату следующего действия (если она есть), потребности
клиента, основные риски, возможные ошибки менеджера и то, что требует
внимания руководителя. Production-ready решение не требовалось — цель:
рабочий и демонстрируемый MVP.

## 1. Архитектура

Пользователь либо выбирает один из 4 тестовых транскриптов, либо вставляет
свой текст и дату разговора в интерфейсе Streamlit (`app.py`). Текст и дата
звонка подставляются в шаблон пользовательского сообщения (`prompts.py`)
поверх системного промпта с жёсткими правилами анализа (запрет на домыслы,
разграничение потребности/риска/ошибки, обработка относительных и
неоднозначных дат). Запрос уходит в Anthropic Messages API (`extractor.py`)
с единственным доступным инструментом `record_case_analysis`, схема которого
жёстко задаёт структуру ответа (structured tool-use) — это исключает
свободный текст и заставляет модель заполнить именно нужные поля. Ответ
инструмента валидируется Pydantic-моделью `CaseAnalysis` (`schema.py`): если
модель вернёт данные не по схеме, приложение получит явную ошибку валидации
вместо тихого использования некорректных данных. Streamlit отображает
результат по 7 разделам, при этом дата и остальные выводы сопровождаются
цитатой (`source_text`) из транскрипта — можно проверить, что вывод не
выдуман. Если `next_action_date.value = null` или `confidence` не `high`,
интерфейс явно показывает это как "дата не определена" с пояснением, а не
молчит и не гадает. Если `ANTHROPIC_API_KEY` не задан, приложение для 4
тестовых транскриптов переключается в демо-режим и показывает заранее
подготовленный вручную эталонный результат (`data/expected_results.json`) с
явной пометкой об этом — MVP остаётся демонстрируемым без живого ключа.
Контроль галлюцинаций держится на трёх слоях: системный промпт с явными
запретами и требованием evidence; принудительная структура ответа через
tool-use вместо парсинга свободного текста; и ручная сверка фактического
результата с вручную определённым ожидаемым результатом по всем 4 тестовым
транскриптам.

## 2. Технологический стек

| Технология | Зачем |
|---|---|
| Python 3.11+ | Реализация; минимум обвязки для 2-часового MVP |
| Streamlit | Готовый UI без фронтенд-кода — специально для демонстрации |
| Anthropic SDK (structured tool-use) | Один LLM-вызов с принудительной JSON-схемой ответа вместо парсинга свободного текста |
| Pydantic v2 | Валидация и типизация ответа модели; ловит некорректный JSON до отображения в UI |
| python-dotenv | Локальная загрузка `.env` для ключа API без хардкода |

Стек выбран по умолчанию как предложенный в задании — для 4 транскриптов и
2 часов он избыточен разве что в части Pydantic, но именно она дешёво даёт
защиту от "полусырого" JSON от модели, поэтому оставлена.

## 3. Структура файлов

```
task-ai/
├── app.py                     # Streamlit UI
├── extractor.py                # вызов LLM (tool-use) + офлайн fallback

├── schema.py                   # Pydantic-схема ответа
├── requirements.txt
├── .env.example
├── data/
│   ├── transcripts.json        # 4 тестовых транскрипта (входные данные)
│   └── expected_results.json   # вручную определённый эталон (тесты + demo fallback)
└── README.md
```

## 4. JSON-схема

```json
{
  "outcome": "string",
  "next_step": "string",
  "next_step_source_text": "string | null",
  "next_action_date": {
    "value": "YYYY-MM-DD | null",
    "confidence": "high | medium | low",
    "ambiguity": "string | null",
    "source_text": "string | null"
  },
  "customer_needs": [{"text": "string", "source_text": "string | null"}],
  "risks": [{"text": "string", "source_text": "string | null"}],
  "manager_mistakes": [{"text": "string", "source_text": "string | null"}],
  "manager_attention": [{"text": "string", "source_text": "string | null"}]
}
```

Отличие от предложенной в задании схемы: `customer_needs`/`risks`/
`manager_mistakes`/`manager_attention` — не массивы строк, а массивы
`{text, source_text}`, чтобы evidence был не только у даты, но у каждого
важного вывода (это прямо было пожелание в задании).

## 5. System prompt

Полный текст — в [`prompts.py`](prompts.py) (`SYSTEM_PROMPT`). Ключевые
принципы: использовать только текст транскрипта; не путать желание клиента с
согласованным действием; не путать потребность клиента с риском проекта;
указывать ошибку менеджера только при явном подтверждении в диалоге и не
пытаться найти её искусственно; относительные даты интерпретировать строго
от даты звонка и только при однозначности; при нескольких/неоднозначных
датах — `value` = ближайшее согласованное действие, остальное — в
`ambiguity`; при недостатке данных — писать это явным текстом в поле, а не
оставлять пустым и не придумывать.

## 6. Инструкция запуска

```bash
cd task-ai
python -m venv .venv
source .venv/Scripts/activate      # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env               # вписать свой ANTHROPIC_API_KEY
streamlit run app.py
```

Без ключа приложение тоже запускается и работает: для 4 тестовых
транскриптов вместо live-вызова покажет заранее подготовленный эталонный
результат с явной пометкой демо-режима.

## 7. Что было проверено

- Ожидаемый результат по всем 4 транскриптам определён вручную ДО
  использования как эталон (`data/expected_results.json`), как и требовалось
  методикой тестирования.
- **Явная/однозначная дата** (Транскрипт 1: "10 сентября в 15:00 по
  Екатеринбургу") → `value` заполняется, `confidence=high`.
- **Относительная дата от даты звонка**: Транскрипт 2 ("завтра" от вторника
  8.09 → 9.09.2026); Транскрипт 3 ("в пятницу", время скорректировано с
  11:00 на 11:30, от понедельника 7.09 → 11.09.2026).
- **Несколько сроков в одном разговоре** (Транскрипт 2: "завтра" для списка
  данных vs "к понедельнику" для расчёта) → в `value` ближайший срок,
  конфликт/второй срок явно описан в `ambiguity`, а не выбран молча.
- **Дата принципиально не определяется** (Транскрипт 4: только "в декабре" и
  "после 20-го числа" без года) → `value=null`, `confidence=low`, понятное
  объяснение в `ambiguity`.
- **Согласованный шаг vs просто интерес клиента**: в Транскрипте 3 Олег
  интересуется контролем звонков, но `next_step` — это именно отправка NDA и
  звонок в пятницу, а не сама идея контроля.
- **Ошибка менеджера только при явном подтверждении**: например, Транскрипт 1
  — менеджер сразу предложила КП на 14 филиалов, клиент прямо возразил
  ("коммерческое сейчас рано"); там, где менеджер не допускал очевидной
  ошибки, `manager_mistakes` не заполнялся искусственно — схема и промпт не
  вынуждают модель находить "хотя бы одну" ошибку в каждом разговоре.
- **Риск отделён от потребности**: например, в Транскрипте 2 "1 ноября
  магазины не должны встать" — потребность, а "кассовая программа
  обновляется сторонним подрядчиком" — риск.
- Синтаксическая проверка всех `.py`-файлов (`python -m py_compile`) — OK.
- Программная валидация `data/expected_results.json` через
  `CaseAnalysis.model_validate(...)` для всех 4 транскриптов — OK (см. вывод
  ниже), ошибок схемы нет.
- **Живой прогон в браузере**: приложение запущено локально (`streamlit
  run`), вручную пройден полный сценарий — выбор Транскрипта 2 → автоподстановка
  текста и даты → клик "Анализировать" → корректный офлайн-fallback (нет
  `ANTHROPIC_API_KEY` в этой среде) → все 7 разделов и JSON отрендерились
  верно. Отдельно проверен Транскрипт 4 (null-дата) — интерфейс корректно
  показал "Дата не определена однозначно (null)" с пояснением.
- Живой вызов Anthropic API в этой среде **не выполнялся**: в окружении, где
  собирался MVP, нет `ANTHROPIC_API_KEY`. Проверен весь пайплайн, кроме
  самого сетевого запроса, через офлайн fallback. Перед реальной
  демонстрацией нужно прогнать хотя бы раз с живым ключом.

```
transcript 1: OK — next_action_date.value='2026-09-10' confidence=high mistakes=1 needs=3 risks=2 attention=2
transcript 2: OK — next_action_date.value='2026-09-09' confidence=high mistakes=2 needs=5 risks=4 attention=3
transcript 3: OK — next_action_date.value='2026-09-11' confidence=high mistakes=2 needs=4 risks=4 attention=3
transcript 4: OK — next_action_date.value=None    confidence=low  mistakes=2 needs=4 risks=3 attention=3
```

## 8. Где решение может ошибаться

- **Множественные относительные даты в одном сообщении** (как в
  Транскрипте 2): модель должна сама выбрать "ближайшее" действие для
  `value` — при более запутанных формулировках может выбрать не тот срок;
  проверено только на 4 примерах, не на большом eval-датасете.
- **Год не указан явно** (Транскрипт 4, "после 20-го числа" января):
  корректно обработано как `null`, но это пограничный случай — при чуть
  иной формулировке модель может излишне самоуверенно домыслить год.
- **Длинные транскрипты** (сильно длиннее приведённых 4 примеров) не
  проверялись — возможны проблемы с удержанием всех деталей в одном
  tool-call и с точностью evidence-цитат.
- **"Ошибка менеджера" частично субъективна**: модель следует явным правилам
  и примерам, но грань между нормальным действием и ошибкой в пограничных
  случаях зависит от интерпретации, а не строго детерминирована.
- **Нет программной сверки `source_text` с исходным текстом** — модель в
  редких случаях может слегка перефразировать цитату вместо дословного
  повторения; это не проверяется кодом, только вручную.
- **Офлайн-режим работает только для 4 подготовленных транскриптов** — для
  произвольного вставленного текста без API-ключа анализ невозможен.
- Один запрос = один транскрипт; нет пакетной обработки, нет сохранения
  истории между сессиями (`st.session_state` сбрасывается при перезапуске
  приложения).

## 9. Следующая итерация

1. **Eval-датасет** из 15–30 транскриптов, включая синтетические пограничные
   случаи (конфликтующие даты, нулевая информация, скрытые ошибки
   менеджера), с автоматическим сравнением по полям вместо ручной сверки.
2. **Автотесты (pytest)**: валидация схемы, регрессия на "не придумывать
   ошибку менеджера", устойчивость к очень длинным транскриптам.
3. **Программная проверка evidence**: `source_text` должен быть (почти)
   подстрокой исходного транскрипта; при несовпадении — явно помечать вывод
   как неподтверждённый цитатой.
4. **Human-in-the-loop**: возможность руководителю отметить вывод модели как
   "согласен/не согласен" прямо в UI, с сохранением обратной связи.
5. **Batch-режим**: загрузка и анализ пачки транскриптов (CSV/JSON) за один
   прогон с выгрузкой сводной таблицы для CRM.
6. **Интеграция с CRM**: автозаполнение карточки сделки (следующий шаг + дата
   + риски) вместо отдельного UI.
7. **Защита персональных данных**: маскирование/детекция ФИО и контактов на
   входе (даже для формально "обезличенных" транскриптов) + учёт требований
   к резидентности данных при выборе модели/региона API (прямо всплыло в
   Транскрипте 3 — клиент требует российский контур).

## 10. Сценарий демонстрации (до 5 минут)

- **00:00–00:30** — Что показываем: одна фраза о задаче (7 полей по каждому
  транскрипту), открыть приложение.
- **00:30–01:30** — Ввод: выбрать в списке "Транскрипт 2 — Зелёная Полка",
  показать, что текст и дата подставились автоматически, нажать
  "Анализировать".
- **01:30–03:00** — Результат: пройтись по всем 7 разделам, отдельно
  показать evidence-цитаты под выводами и раскрыть "Исходный JSON".
- **03:00–04:00** — Сложный случай: переключиться на "Транскрипт 4 —
  Север-Транс" — `next_action_date.value = null` с понятным объяснением
  (нет точного числа, год для января не назван); затем вернуться к
  Транскрипту 2 и показать, как в `ambiguity` явно виден конфликт "завтра"
  vs "к понедельнику".
- **04:00–05:00** — Архитектура и ограничения: Streamlit → системный промпт →
  structured tool-call → Pydantic-валидация → офлайн fallback; и 2-3 ключевых
  ограничения (нет батч-режима, нет автоматической сверки evidence,
  протестировано только на 4 примерах).
